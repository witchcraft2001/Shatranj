# S10 — UNETLD backend selection and lifecycle

## Test media

- MAME: `build/sprinter/SHATRANJ-SMOKE.IMG` only. It contains `SHATRANJ.EXE`, `UNETESP.DLL`, `UNETRTL.DLL`, and `UNET509B.DLL`.
- Hardware: `build/sprinter/SHATRANJ-HW.zip`. Unpack all four files into one directory; DSS APPINFO lets libman locate the DLL beside the EXE.
- Use the same EXE from this build on either medium. Verify its SHA-256 against the handoff message before testing.

## Expected behavior

1. Bring up each available adapter with its backend kit, then open Shatranj's NETWORK screen. Before the first preflight the backend row shows `--`, without stray characters. Once connecting, `NET=WIFI` displays `UNETESP.DLL`, `NET=RTL` displays `UNETRTL.DLL`, and `NET=509B` displays `UNET509B.DLL`. The preflight should complete and DIRECT/MQTT should connect as in S9 when a peer is available. The backend kit must publish `NET` and its other network settings before Shatranj starts.
2. Lowercase `wifi`, `rtl`, or `509b` should select the same DLL. `WIFI` remains the ESP alias; the other tags form `UNET<TAG>.DLL` directly.
3. Missing or empty `NET` reports `NO NET ENV`. Values outside 3–4 letters or digits, such as `FOO!` or `AB`, report `INVALID NET VALUE`. A valid tag without a matching DLL reports `DLL LOAD FAILED` and still shows the selected filename.
4. With a deliberately substituted incompatible DLL, the failure should identify the stage: `DLL INFO FAILED`, `DLL NAME MISMATCH`, `DLL CALL/GETCAPS FAILED`, or `uNet ABI MISMATCH`. A DLL without TCP reports `BACKEND HAS NO TCP`. Failed STATUS and NETINIT report `ADAPTER STATUS FAILED` and `NETINIT FAILED` respectively; dispatcher failures during NETSTART report `NETSTART CALL FAILED`. Restore the supplied DLL after each negative test.
5. Revisit NETWORK after disconnecting: the already initialized DLL should be reused. Retry after a failed preflight: the previous handle should be released before another load. Exit to DSS: CLOSE, NETDONE, and DLL unload should complete without a freeze or stack trap.
6. Repeat the normal DIRECT and MQTT session checks from S9 for every adapter available in the test environment, including a reconnect after a completed game. The selected DLL name must remain visible on both transport screens.
7. Supply a long `NETHOST` or `NETPORT` (up to DSS's 255-character limit), then open NETWORK. Defaults must fit their respective editor fields, remain NUL-terminated, and leave adjacent fields intact. Restore usable settings before connecting.

## Automated coverage

`make sprinter-check` covers all three tags in both cases, absent/empty NET, invalid characters and lengths, each LOAD/GETCAPS/STATUS/NETINIT error, missing TCP, successful reuse, release before retry, and idempotent shutdown. The lifecycle fixture starts with dirty compact state and checks guard depth and enabled interrupts at every loader/dispatcher boundary. Regressions verify initialization before the screen reads the DLL name, bounded ENV_GET copying, and shutdown after a rejected ABI without CLOSE or NETDONE.

Both media builders read every member back and compare it with its input. The gate rebuilds both containers and requires byte-for-byte determinism. Assembly assertions bound the main WIN2 code pool, the tail after the IM2 table, and the 315-byte loader state plus shared staging buffers. At the S10 handoff the main code pool had 4 bytes free, the tail 28 bytes, and LOWRAM_NET_GATE 20 bytes; subsequent changes must respect these checks.

Record each tested adapter and medium separately. Real hardware remains **pending** until each card is exercised on a physical Sprinter; a passing MAME or build check does not establish hardware behavior.
