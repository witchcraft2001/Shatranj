# Sprinter tester notes — S1: PRELOAD, video mode, vsync platform stand

Stage S1 delivers the first real platform stand: the PRELOAD loader,
manifest, flat two-page resident, the IM2 interrupt chain (port.md section
3.9), and a video stand exercising palette/grid/flip/accelerator/WIN0/mode
switch. This protocol has two parts: host-side automated checks (fast,
always run first) and a manual MAME run (the actual DoD).

Per CLAUDE.md: hardware is not substituted by a green CI/emulator run.
Everything below MAME confirms the *code*; the real-hardware line at the
end of this file stays "pending" until run on Sprinter itself.

## Prerequisites

- Same as `docs/sprinter-testnotes/S0.md` (git, GNU make, Python ≥ 3.10,
  z88dk, mtools) plus:
  - `sjasmplus` v1.22.0 in `PATH` (`sjasmplus --version`).
  - `z88dk-ticks` for the z80 unit tests (falls back to
    `/Users/dmitry/dev/zx/sprinter/z88dk/bin/z88dk-ticks` if not in `PATH`).
- A MAME build with `sprinter` support. S1 does not touch networking, so
  the release build works:
  `/Users/dmitry/dev/zx/sprinter/mame_images/mame_release_v306_25.05.2025/`.

## Protocol

### 1. Host-side automated checks

```sh
make sprinter-check
```

Expected output ends with:

```
[OK] sprinter-gates: R1/R3 static policy checks green
...
[OK] SHATRANJ.EXE sha256 <digest> ...
[OK] sprinter-check: deps, EXE format, smoke image (deterministic)
```

- [ ] `sprinter-check` is green: layout self-test, EXE-format tests, R1/R3
      gate self-tests + real-tree scan, all three z80 unit tests
      (`t_manifest`, `t_im2_table`, `t_frame_wait`), the resident byte
      tests, and the deterministic smoke-image rebuild.
- [ ] Note the reported EXE sha256 for the sign-off table below.

### 2. Pin-drift and R1/R3 trap checks (gates must trap, not pass silently)

```sh
git -C extern/sprinter-libs checkout HEAD~1
make sprinter-deps-check   # MUST fail with a commit mismatch message
git -C extern/sprinter-libs checkout 2c58d793cda75dab7e0b2d2836221f089ad8660b
```

- [ ] The deps gate fails loudly on the moved pin and passes again after
      restoring it (same trap as S0).
- [ ] `python3 tools/check_sprinter_accel.py --self-test` and
      `python3 tools/check_sprinter_win0.py --self-test` both print `[OK]`
      — these self-tests already exercise the trap (a fixture with `di`
      removed from an accelerator sequence, and one with a direct
      `OUT (WIN0_PORT)` outside the macros, must both be rejected). No
      manual edit of the real source is needed to see this; the self-test
      fixtures are the trap check.

### 3. MAME manual run

Launch (mirrors the project's own `shatranj.sh` launcher in the MAME
release directory; run from inside that directory so the relative `./IMG/`
paths resolve, or substitute absolute paths):

```sh
cd /Users/dmitry/dev/zx/sprinter/mame_images/mame_release_v306_25.05.2025
./mame sprinter \
  -skip_gameinfo -video opengl -window -nofilter \
  -beta:wd179x:0 525qd -beta:wd179x:1 35hd \
  -flop2 /Users/dmitry/dev/zx/sprinter/sources/Shatranj/build/sprinter/SHATRANJ-SMOKE.IMG \
  -isa0 zxbus_adapter -isa0:zxbus_adapter:card neogs \
  -hard1 ./IMG/sp_hdd_sys.chd -hard2 ./IMG/sp_hdd_media.chd \
  -ata2:0 cdrom -cdrom ./IMG/SprinterCD.iso \
  -bios v3.06
```

DSS boots from the hard-disk image (`-hard1`); the smoke image is only the
`-flop2` floppy carrying `SHATRANJ.EXE` + the two uNet DLLs (unused by S1,
but `make_sprinter_smoke_image.py` always includes them for a stable,
single test medium — see CLAUDE.md). At the DSS prompt, switch to the
floppy drive holding the image and run `SHATRANJ.EXE`.

- [ ] **P1 — boot.** Banner prints, mode switches to 640×256, the palette
      shows a visible 16-stripe grid, and the hex tick counter/RTC line
      are legible.
- [ ] **P2 — tick rate.** The hex tick counter advances at a steady rate.
      Compare ~50 increments (`0x32`) against 1 second of the RTC seconds
      field (or a stopwatch if RTC shows `-- -- --`, meaning BIOS
      CMOS_TEST reported no working clock in this MAME configuration —
      degrade gracefully, do not block on it; note DSS SysTime itself
      would happily return default time on such a machine, which is why
      the stand probes the BIOS explicitly).
- [ ] **P3 — RR0 discrimination.** Hold a key down and type rapidly for a
      few seconds. The tick counter must **not** accelerate or stall —
      confirms the IM2 stub's SIO RR0 bit-0 check correctly tells frame
      ticks apart from keyboard interrupts (port.md section 3.9). Also
      toggle the rus/eng keyboard layout a few times while the stand runs:
      layout switching is DSS-side work in the `#0038` chain and must
      neither stall the ticks nor break the hotkeys. Occasional one-frame
      hiccups *while keys are in flight* are within spec: with a scancode
      pending, RR0 bit 0 makes the stub deliberately skip that tick
      (port.md section 3.9); sustained acceleration or a stall is the
      failure signal, not isolated jitter.
- [ ] **P4 — flip (hotkey `1`).** The visible stripe pattern changes
      (buffer 1's stripe 0 is forced white as a marker) and changes back
      on a second press, with no visible tearing/garbage. The tick
      counter/RTC line is drawn only on buffer 0, so it disappears while
      buffer 1 is shown — expected, not a defect; it must still be
      advancing normally after flipping back.
- [ ] **P5 — accelerator smoke (hotkey `2`).** A `P` or `F` glyph appears
      near the bottom-left. `P` = FILL_H/FILL_V/COPY_H all read back
      correctly after the accelerated write. **Informational only per
      port.md's risk note** — MAME's accelerator emulation is not
      confirmed; a `P` here is encouraging but the real-hardware run is
      authoritative for this probe specifically.
- [ ] **P6 — WIN0 probe (hotkey `3`).** Same `P`/`F` slot: `P` means the
      WIN0-under-DI remap read back the resident's own "SHS1" header
      correctly through two windows at once, and DSS answered a ScanKey
      poll afterward (still alive). Also confirm the tick counter keeps
      advancing normally afterward (no lingering WIN0 corruption).
- [ ] **P7 — mode switch (hotkey `4`).** Screen briefly shows the 320×256
      mode, then returns to 640×256 with the palette and grid correctly
      redrawn (no stale garbage from the mode change).
- [ ] **P8 — mouse liveness.** If a mouse is attached, move it: the
      standard DSS cursor should track normally. S1's ISR does not touch
      mouse handling itself (it tail-jumps into DSS's own `#0038` chain,
      which owns the cursor) — this probe is confirming the tail-jump
      didn't break DSS's own handling, not exercising port-specific code.
- [ ] **P9 — soak (DoD).** Leave the stand running (no keys) for
      **≥ 10 minutes**. Tick counter must stay close to 50/s the whole
      time (spot-check against RTC or a stopwatch at the start and end);
      no visible corruption, no hang.
- [ ] **P10 — clean exit (hotkey `Q` or `q`).** Screen returns to the
      pre-launch video mode, DSS prompt is clean and responsive
      (`DIR`/any command works normally, typing works in both rus and eng
      layouts) — confirms R11 exit discipline (IM2 uninstalled, mode
      restored, PORT_Y parked).
